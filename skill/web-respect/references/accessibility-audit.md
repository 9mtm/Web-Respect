# Accessibility evaluation

Determine applicable service, public/private context, jurisdiction, sector, effective dates and exceptions before selecting the legal standard. WCAG 2.2 is a technical starting point; applicable legislation/contracts may reference a different version or additional requirements. A widget or successful automated scan cannot certify a whole application.

Inventory representative journeys: landing/navigation/search, forms/error recovery, account creation/login, checkout/payment, support, privacy requests, consent choices and accessibility controls. Include authenticated states, dynamic components, embeds, downloads/PDFs, video/audio, canvas/3D and third-party content. Record sample scope, versions, viewport, browser and assistive technology used.

Use available automated tools for detectable issues, then manually test keyboard navigation, focus visibility/order/return/traps, headings/landmarks and accessible names, screen-reader announcements, errors/status messages, dialogs, language/RTL, contrast, zoom/text resize, reflow, reduced motion, pointer target interactions, drag alternatives, captions/transcripts and authentication barriers. Check consent refusal and deletion-request flows with the same rigor as checkout. Respect existing user preferences and host styling.

Tie findings to the exact success criterion, affected journey, observed behavior, reproduction and user impact. Distinguish definite failures from items needing manual assistive-technology review. Automated absence of findings is not conformance. If screen-reader/browser/device access is unavailable, state the missing test instead of inventing coverage.

Fix source components and underlying content in the authorized scope. Keep Web Respect controls optional and reversible; do not rely on visual overlays to repair semantics or hide failures. Recheck affected journeys and regressions. Provide accurate accessibility statement/contact/help guidance based on actual audit evidence; never fabricate certification.
