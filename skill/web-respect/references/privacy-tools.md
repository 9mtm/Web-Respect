# Cookie Checker and deletion integration

## General discovery-to-integration workflow

This workflow adapts the general package to the current host project; it is not tied to Dpro's website or a fixed vendor list. The agent performs repository/configuration discovery and prepares code. The browser Cookie Checker contributes only a local snapshot.

1. Inspect the host's instructions, package/runtime versions, auth/session patterns, deployments, SDK imports and actual initialization. Use [data flows](data-flows.md) to trace browser calls, API proxies, workers, CMS plugins and server services. Inspect environment variable names and redacted settings without printing credential values. Reconcile dependencies with active calls/configuration; keep unconfirmed candidates distinct from actual processors.
2. Produce a private service registry with purpose, evidence, provider identity, host resource ownership, subject identifier mapping, stored data categories, retention and deletion capability. Include the site's own databases, files, search indexes, backups, queues, logs and AI-related stores. Do not limit discovery to visible cookies.
3. For AI, follow prompts, files/attachments, response or conversation IDs, embeddings/vector stores, telemetry/evaluation stores and provider retention settings. Determine which resources are per-user versus shared. Never delete an entire shared project, vector store or provider account to satisfy one user's request. A generic inference API may not offer individual deletion; mark its actual retention/request process instead of inventing an endpoint.
4. Verify each provider's current official deletion documentation and the host tenant's permissions/configuration. Choose a supported API adapter, a verified approved manual-request channel, a documented restriction, or unsupported/unknown. Record whether acceptance is asynchronous and what establishes completion. Keep API secrets, contact destinations and subject-resource mapping server-side.
5. Within authorized implementation scope, prepare the host's protected request endpoint, durable request/job store and provider registry using the installed Web Respect APIs. Generate concrete adapters for verified APIs and host data stores. Add explicit configuration requirements for missing credentials/tenant settings; do not activate incomplete connectors or substitute fake success. Queue manual work for unsupported APIs without sending messages merely because the skill was installed.
6. Wire the visitor confirmation through `privacy.requestDeletion`, authenticated subject resolution and the host worker's `dispatchDeletion`. Route to actual configured services relevant to that subject. Persist per-provider states and minimal evidence. Build idempotent resource-scoped operations, locks/retries/checkpoints and restore restrictions. Deletion and consent withdrawal remain separate workflows.
7. Test synthetic subjects, authorization, subject isolation, duplicate delivery, partial failure, retention restrictions and completion evidence. Deliver an integration summary showing each discovered service's evidence, prepared adapter, tested behavior, missing configuration and manual/unsupported cases. Ask for missing facts only after inspecting what the project exposes; never describe an unconfigured adapter as working.

All of this can be prepared for any supported host project. Discovery does not grant permission to send real vendor requests, contact companies or delete production records. Preparing tested code is distinct from executing it on real users.

## Package APIs

For package 0.3.0 or newer, use `scanCookies` from `/scanner`, `mountPrivacyControls` from `/browser`, or `mount(..., {privacy: {...}})` to add controls to the consent dialog. Confirm the installed version first; 0.1.2 lacks these APIs. Configure translated labels for the host locale.

The scanner reads visible cookie names, storage key names and resource hosts on the current page. Values are not included; nothing is sent. Default signatures cover possible Google Analytics, Tag Manager and Meta Pixel use; supply host-specific rules for other services. Treat matches as evidence to investigate. Preserve unknown and unavailable states. It cannot discover HttpOnly cookies, other-origin storage, server SDKs, private AI calls, account mappings or retention settings. Do not upload raw reports without reviewing key names for personal data.

Configure `privacy.requestDeletion` only after implementing the host's protected request endpoint. The callback takes no subject identifier; resolve identity server-side through the host's session or proportionate verification. Return `{requestId, status: 'pending'|'completed'|'restricted'}`. Visitor confirmation submits a request, not an instruction to delete arbitrary records. No callback means the deletion button is absent. Do not enable a mock receipt in production or report a demo as a real request.

Use `dispatchDeletion` from `/privacy` only in a server worker. Supply `authorize`, a durable `record` callback and subject-specific `providers` (unique `id`, `requestDeletion(context)` returning `pending`, `completed` or `restricted`). Include the host database and actual configured AI/CRM/storage processors. Persist intent before contacting a provider. Credentials, subject-resource mappings and approved recipient configuration stay server-side. Never use browser scanner matches as automatic destinations.

The helper is not a durable queue or a prebuilt vendor connector. Add per-request locks, idempotency keys, retries/checkpoints, scoped legal holds and restore protection. Vendor acceptance remains pending until confirmed; failed callbacks remain failed and require retry/reconciliation. Read the installed package's docs/privacy-tools.md for API examples. Verify current official vendor documentation before implementing a specific API; document unsupported or manual paths.

Test with synthetic subjects and assert no calls on unauthorized requests, no cross-subject access, no automatic deletion after mere consent withdrawal, no repeated destructive work on retries and no false completion during provider failure. Installation does not authorize sending real vendor requests or running deletion on real users. Describe implemented capabilities and outstanding host/provider setup accurately in the site's README and product page.
