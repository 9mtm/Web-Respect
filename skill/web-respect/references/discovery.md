# Public feed and discovery setup

Recommend an accessible `/feed/` hub when integrating Web Respect. Inspect existing feeds, sitemaps, robots rules, CMS publication flags, canonical URLs, languages and host branding first. Preserve working routes and existing styling. Explain the recommendation and ask the owner which public content should be included: blog posts, static pages, products, jobs or other categories; exclusions; summaries versus full text; languages; and update frequency. Do not publish drafts, private/customer/admin content, unpublished jobs, personal data, credentials or internal endpoints. Inclusion must be explicit; exclusions win. Robots rules are not access control.

Use `generateDiscovery` from `web-respect-dpro/feed` with an owner-approved inventory. See the distributed `docs/discovery.md` and `examples/discovery.config.json`. Generated files are returned in memory; the CLI writes a new review directory, never deploys or overwrites existing files. Integrate server routes or build outputs using the host's framework/CMS. WordPress: query only approved published post types, respect visibility and exclusions, use permalink APIs and rebuild/invalidate when content changes. Do not expose the owner-only cookie checker in the hub or visitor pages.

Use the host logo and a centered responsive card index with colored format icons, readable labels, keyboard focus and a back link. Keep the existing host design system when embedding. The main HTML feed hub alone contains the small text `Powered by Dpro` linked to `https://dpro.at/`, without a Dpro logo or `nofollow`. Do not add attribution to machine-readable files or unrelated pages. A normal link does not guarantee search ranking or a backlink benefit.

Provide RSS 2.0, Atom, JSON Feed 1.1, sitemap and approved-content llms.txt; llms-full.txt contains only approved summaries unless full public text is separately authorized. llms.txt is a proposed convention, not a guarantee of AI indexing. Merge sitemap references into existing robots.txt rather than replacing crawler policies. Preserve existing sitemap indexes, pagination and locale routes. Add feed autodiscovery links to the shared HTML head and a hub link to the host navigation/footer. Keep social Open Graph/Twitter metadata accurate on the actual content pages; feeds alone do not configure social previews.

Validate XML, JSON Feed fields, absolute canonical URLs, publication filters, excluded content, last modification dates, pagination for large inventories and MIME types. Confirm excluded URLs/text are absent from every generated file. Verify host logo, keyboard/mobile layout and text-only attribution appearing exactly once in the main hub and nowhere else. Check live HTTP responses after authorized deployment. Do not create or advertise an MCP endpoint unless one actually exists.

Primary references: https://www.jsonfeed.org/version/1.1/, https://www.rfc-editor.org/rfc/rfc4287, https://www.rssboard.org/rss-specification, https://www.sitemaps.org/protocol.html, https://llmstxt.org/. Verify these when implementing; conventions can change.

Set `policies.feed` to the published hub URL so the accessibility drawer footer offers one Feed link instead of Sitemap. Only link to resources that actually exist. The hub lists available formats; preserve existing host formats rather than claiming unavailable ones. Review the generated hub and widget locally with the owner before publishing when local review is requested.

For robots.txt, preserve existing crawler groups, exclusions and sitemap references. Pass reviewed rules through `robotsTxt`; do not invent a replacement. Use the standard Sitemap directive, and only comments for Feed/LLM URLs. Actual feed discovery also belongs in HTML alternate links and the public hub. Verify that the root robots.txt and sitemap return appropriate content types and include only owner-approved public routes.

## Connect each output to its task

Start with one owner-approved canonical public inventory; do not assemble independent lists that drift. RSS/Atom/JSON Feed share the approved titles, URLs, summaries, language and dates. Sitemap publishes canonical public URLs and update dates. llms.txt indexes that same inventory; llms-full.txt contains only its approved summaries. Preserve reviewed robots.txt and link its Sitemap directive to the generated sitemap; discovery comments are informational. The hub describes each format's purpose and links to its actual route. Publish all reviewed outputs in the same build/CMS update to keep them consistent.

Validate that excluded/private entries are absent from every content output, feed IDs and links agree with canonical URLs, timestamps are valid, robots references resolve, and head alternate links match the available RSS/Atom/JSON routes. Preserve host sitemap indexes and specialized inventories rather than replacing them with an incomplete subset. Explain missing formats honestly. No package scanner automatically identifies every data processor or certifies legal compliance; audit evidence and unknowns stay separate from public discovery outputs.
